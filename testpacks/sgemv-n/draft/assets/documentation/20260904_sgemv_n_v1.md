## 2. 为什么这样优化

SGEMV-N 计算 `y = alpha*A*x + beta*y`。矩阵按列连续存储时，原始单列
内核每处理一列都要重新读写一次 `Y`。算法只有约 `2*M*N` 次浮点运算，
算术强度低，FT2000 上主要受访存与加载延迟限制，而不是 FMA 峰值限制。

本轮从以下三个约束出发：

1. **减少 Y 流量。** 4列内核同时处理4列，`Y` 每4列只加载和回写一次；
   2列内核每2列读写一次。与单列相比，它们分别将主循环中的 Y 流量降为
   约1/4和1/2。
2. **用独立 FMA 链隐藏延迟。** 4列×16行内核使用4个 Y 向量累加器，
   交错执行4列的 FMA；2列×32行内核使用8个 Y 向量累加器。这样既保持
   顺序 A 访问，也在32个 AArch64 SIMD 寄存器内提供足够多的独立指令。
3. **控制高线程下的并发 A 流。** 16个 worker 强制4列会同时产生最多64条
   A 流，小局部行块无法建立稳定流水。2列把它降到32条；局部块过小或
   已进入带宽饱和区时，原始单列的16条流更稳。

最终选择规则为：

```text
local_m = ceil(M / workers)

workers < 16                         -> 4列×16行
workers >= 16 且 64 <= local_m < 512 -> 2列×32行
workers >= 16 的其他情况             -> 原始单列
```

`N` 不能整除4或2时由原始单列尾部继续处理；非单位 `incy` 保留原有标量
路径。模式参数只在 `FT2000 && single && real && GEMV-N` 时启用，避免再次
影响 DGEMV-N、SGEMV-T、复数或其他平台。

改动文件：

- `source/kernel/arm64/gemv_n.S`
- `source/driver/level2/gemv_thread.c`

## 3. 探索实验与取舍

- 强制4列证明交叉流水有效：1线程 `4096×4096` 约提升39%，8线程
  `1024×16384` 约提升37%；但16线程、`M=512/1024` 的宽矩阵因并发 A 流
  过多而回退。
- 强制2列在16线程 `1024×16384`、`1024×32768` 相对内部原始核分别约
  提升23.75%和23.57%，`4096×4096` 约提升26.92%；但 `M=512` 和
  `M=16384` 分别回退约3.87%和1.27%，由此确定局部行数边界。
- 将多列核预取距离由512字节改为 release033 单列核使用的768字节后，
  单线程3个代表点回退约8%--12%，`4096×4096@16` 也回退约4%。多流内核
  每条流的推进速度与单流不同，不能直接照搬单流预取距离，因此最终保留
  512字节。

## 5. 正式性能测试方法

服务器有32核、2个 socket/NUMA 节点，每节点16核；正式测试只使用 NUMA 0：

```text
CPU：0-15
内存：NUMA 0
OMP_DYNAMIC=FALSE
OMP_PLACES=cores
OMP_PROC_BIND=spread
OMP_WAIT_POLICY=ACTIVE
```

两个版本配置均为 OpenBLAS 0.3.33、`USE_OPENMP`、`TARGET=FT2000`、
`MAX_THREADS=32`。候选构建命令为：

```bash
make -j32 shared NO_LAPACK=1 TARGET=FT2000 USE_OPENMP=1 NUM_THREADS=32
```

每个点预热3次，两个版本按奇偶轮反转顺序并各测5轮。表中分别取5次
GFLOPS 中位数，再计算：

```text
加速比 = v1 GFLOPS 中位数 / release033 GFLOPS 中位数
```

标准16M元素矩阵使用1、8、16线程；另外保留两个此前 DGEMV-N 验收关注的
大规模点。单线程循环60次，多线程标准点160次，`8192×8192` 60次，
`16384×16384` 30次。

| 全部正式点 | 11 | 1.1426× | +14.26% |

性能收益集中在宽矩阵和方阵：多列核既减少 Y 流量，又打散 FMA 依赖；
16线程宽矩阵使用2列后避免了4列的 A 流过载。高矩阵的 `N` 较小，Y 重复
次数本来较少，且 A 流量占主导，因此8/16线程已接近带宽上限，结果基本
持平。两个大规模点也已进入约22.3--22.5 GFLOPS 的平台区，继续增加列数
不能增加内存带宽；选择器在这里保守回退，避免此前出现的1%--2%回退。

唯一稳定的小回退是 `1024×16384@1` 的1.16%。探索数据表明4列与内部原始
512字节预取核在该点本身接近持平，而 release033 的原始核使用768字节预取；
把768字节直接用于多列核会造成更大范围回退，因此没有为单个点牺牲整体。
