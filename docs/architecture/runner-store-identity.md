# Runner 数据库身份与恢复边界

Runner 的机器身份描述硬件与运行环境；`runner_id` 可以由配置指定，两者都不能区分同一机器上不同的 Runner 数据库。Runner 在 SQLite 的 `runner_metadata` 中创建随机 `store_instance_id`，并通过 `/health` 和 `store_identity_guard` 能力公布。重启沿用同一 ID；并发初始化旧数据库时通过原子插入选定同一个 ID。升级只为数据库建立身份，不修改已有实验或声称历史提交已验证身份。

新正式实验将数据库 ID 和执行计划一同保存；新复现实验在提交认领事务中保存该 ID，独立测试、试跑和分支构建在提交前保存 ID。控制端将客户端绑定到该 ID。绑定后的 RPC 使用 `/_corepilot/runner-stores/<id>/...`：新 Runner 在处理提交、查询、取消、命令、测量、日志和 HTTP 归档上传之前核对 ID；不同数据库返回 `RUNNER_STORE_MISMATCH`。旧 Runner 不认识该路径，控制端不会退回无保护路径。客户端在探测到新能力后也会在后续 HTTP 请求中使用该路径。

新正式实验、复现、独立测试与试跑要求 Runner 同时支持数据库身份保护和库产物路径核对；只构建分支基线要求数据库身份保护。旧版缺少能力时提示升级，提交前停止。已有作业的查询和取消不以新增的路径核对能力为条件。独立测试在创建记录前拒绝已识别的旧生成适配器，并按所选模式检查生成脚本所需 API；同一幂等请求重放仍读取已保存的历史任务。

历史已提交记录没有固定 ID 时，保留原记录和本地可读内容，不根据当前连接补填身份；自动查询、取消或恢复保持未确认状态，由维护者检查原 Runner 和作业。可证明尚未提交的历史准备任务仍可按新规则提交。完成的历史测试无本地结果缓存时保留已确认执行状态，不把缺失缓存当作执行失败或未知。

这是数据库谱系标识，不是机器认证或防篡改证明：完整复制数据库会复制同一个 ID，也不能识别蓄意伪装的服务。旧客户端仍可使用兼容的无保护路由；反向代理必须可信且原样转发保护路径，版本混用或未转发时应检查部署。SSH/SCP 的暂存使用另一传输边界，数据库 ID 不证明 SSH 与 Runner 指向同一台机器。开发实验恢复尚未全部接入该身份保护。

离线测试通过本地 HTTP Runner、SQLite、双进程和故障代理验证数据库重启、竞争初始化、数据库复制、同地址替换、响应丢失、取消与原作业恢复；这些测试不是目标 CPU 性能证据，也不访问真实远程机器。
