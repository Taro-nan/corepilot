## 本轮实施与验证

### 本机配置跟踪

- **原始问题**：根目录 `corepilot.yaml` 与 `.tmp-model-test/config.json` 原本已被 Git 跟踪，后者即使位于忽略目录仍会进入克隆；前者含机器专用配置。
- **决策和修改**：仅从当前索引移除两项，保留原本地文件；`.gitignore` 忽略根配置，`scripts/check-repository.mjs` 拒绝跟踪配置、运行数据和临时模型测试目录，公共示例保留在 `examples/`。
- **针对性测试**：`node --import tsx --test --test-concurrency=1 tests/repository-hygiene.test.ts`，3 项通过；测试使用隔离 Git 仓库验证强制加入本机配置会失败、移出索引后原文件仍存在。
- **限制**：当前分支的删除不会清除既有 Git 历史或已推送副本；本次不擅自重写历史。

### 候选源码符号链接

- **原始问题**：`WorkspaceToolset` 检查中间目录链接，却允许最终路径为符号链接；读写最终链接可能访问工作区外的文件，包括独立 oracle。失效链接因 `existsSync` 返回 false 也未被识别。
- **修改**：所有路径分量使用 `lstatSync` 检查，包括最终分量和失效链接；现有的源码范围检查继续执行。
- **针对性测试**：`node --import tsx --test --test-concurrency=1 tests/workspace-tools.test.ts tests/library-package.test.ts`，24 项通过。本机 Windows 测试末尾和中间目录 junction 及外部文件保持不变；普通文件链接和失效文件链接已编写 Linux 测试，尚待执行，本机没有创建文件符号链接的权限。
- **限制**：这是应用层路径约束，不能防止其他进程在检查与使用之间替换路径，也不能约束任意构建命令。需要系统级资源/权限隔离才能进一步收紧这些边界，不能把本次修复称作完整沙箱。
- **补充核查**：旧版无 Package 的工具写入只按区分大小写的根目录名保护 `.git`，嵌套仓库的 `.git` 与大小写变体也可能被写入。现在源码范围解析、Package 范围与所有写入工具统一拒绝各层级的 Git、CorePilot 运行目录和 `node_modules` 元数据。`tests/workspace-tools.test.ts`、`tests/library-package.test.ts`、`tests/source-optimization-flow.test.ts` 集成 37/37 通过，覆盖大小写、嵌套路径和原始文件不变。

### 源码任务的用户授权范围

- **问题**：旧 `source_only` 任务仅由 Agent 声明假设涉及的文件，用户的调查入口并不限制写入；离线复现中，Agent 可自行选择测试参考文件并将其冻结为候选。
- **修改**：新任务从网页、HTTP、CLI 和交互工作台明确接收可修改文件或目录，固定到幂等身份、Task 与执行契约；假设、写工具及相对原基准的累计候选改动共同受限。`--file` 仍只是调查入口。交互式 `/optimize --source-only` 同时修复模式和授权未传入后端的问题。
- **历史兼容**：历史候选保持原样并可查看、独立测试；首次继续时要求明确后续范围，已有工作区改动须在范围内；授权及继续状态事务保存，原候选与旧执行摘要不回写。范围不自动识别用户项目内的测试或 oracle，选择目录前仍须人工确认。
- **针对性验证**：独立工作区源码、公开 API 和事务测试 19 项、Package 测试 18 项及 CLI 单项 3 项通过；浏览器新建、预检和历史继续 3 项通过。均为本机模型与 Runner 夹具；最终合并版本的全量回归另行记录。

### 自动验证任务的源码授权与旧实验恢复

- **问题**：非 Package 的 `verified` 请求可以引用正式 evaluator，但未固定 Agent 可写范围；旧 API 同时错误地拒绝用户传入范围。工作流只检查每次候选增量，缺少相对原基线的累计约束。
- **修改**：网页、CLI（含交互工作台和项目预检）与 HTTP 共用范围解析及预检；新无 Package 任务固定授权并纳入幂等与执行身份，Package 拒绝覆盖。假设、写工具和候选冻结分别检查范围；冻结另检查相对原基线累计变更。历史任务首次继续编辑时对现有工作区核验后事务追加授权，原 Task 目标、旧摘要、候选及实验保留。
- **恢复与限制**：旧无授权任务可对账已有未终态的正式实验或复验，且不启动新模型或实验；已结束候选可使用原 `retry-validation` 创建新验证。原正式实验对账成功后停在待复验，不自动创建复验。旧 `development-job` 单独存在于 Agent 会话且未固定 Runner 数据库身份，尚不能在无授权时安全自动对账；需保留现场由维护者核对。用户授权范围可能包含测试、oracle 或构建脚本，路径约束本身既不证明参考实现独立，也不是 OS 级隔离。
- **针对性验证**：`node --import tsx --test --test-concurrency=1 tests/verified-source-scope.test.ts` 6/6；`tests/optimization-session-flow.test.ts` 12/12；`tests/candidate-editing.test.ts` 8/8；`tests/web-api.test.ts` 12/12；`npm run test:web -- verified-source-scope.spec.ts` 4/4。模拟 HTTP Runner 的 4 项恢复测试分别覆盖 active ID、仅创建意图、缺计划与缺 Runner 数据库身份；前两项只查询原 ID，后两项无远程请求，均不发送新实验；模型凭据引用失效时仍可对账和重试冻结候选。使用本机 Git、SQLite、HTTP 和模拟模型/Runner 夹具，未启动真实远程优化；Windows 本机 `npm run build`、`npm run typecheck` 与 `npm run check:repo` 通过。
- **首轮全量回归留痕**：在尚未完成新契约夹具调整时执行 `npm test`，474 项中 461 通过、12 失败、1 项因本机文件符号链接权限跳过；不能把该次运行视为全量通过。失败包括：`candidate-editing.test.ts` 两个未授权 verified 创建；`execution-machines.test.ts` 的机器预检；`optimization-report-flow.test.ts` 的交互 `/check`；`remote-execution.test.ts` 的 active/unlinked/legacy-plan 三个 Package 恢复夹具误传用户范围；`testing-api.test.ts` 中“verified 拒绝授权范围”的旧契约断言；`web-api.test.ts` 四个无 Package 的创建、预检及分支测试。现保留这些测试，按真实文件 `kernel.c`（产物测试另有 `temporary.o`）授权或沿用 Package，并将过时的拒绝断言改成缺失/非法授权拒绝与两种模式一致。最终版本的全量 Node 和浏览器回归须分别记录，定向通过不代替全量。

### 同源码树的候选历史提示

- **问题**：本地夹具复现 `C1 → C2 → C1` 的三个不同提交，其中首尾 Git tree 相同，但仍各自创建正式实验；已有历史工具没有将当前未提交源码与旧候选对照。
- **修改**：公开优化 Agent 可在提交前调用 `inspect_candidate_history`，预览与候选 checkpoint 相同的源码树，并查看本任务关联假设中的匹配候选和实验事实。模型可以据此停止或明确选择重测；不会复用旧结果、自动拒绝提交或阻止独立复验。临时 Git 索引不修改原索引、HEAD 和源码，但会写入未引用 Git 对象，且 Git 可能运行项目配置的 clean filter；不提供系统级沙箱。源码或 filter 输出在预览后仍可能改变。

### 实验结果与统计规则的核对

- **数值边界修复**：用有限正数 `1e308` 构造偶数次 A/A 样本时，旧实现的中位数溢出为无穷大，最终将不可计算的区间错误显示为“兼容 1×”；极小/极大值也可能使比值下溢，或仅在重采样时溢出。初次新增测试实际复现失败。现在检查中位数、比值、几何平均与每次重采样的有限性，无法表示时返回 `INVALID`、不生成区间；试跑汇总保留原始样本，显示原因，并使本次试跑不能通过。Runner 执行完成状态不被改写。有限有效计算继续沿用 v3 原方法和固定策略，历史记录不回写。
- **验证**：Node 22.19.0 下 `tests/performance-statistics.test.ts`、`tests/validation-trial-summary.test.ts` 和 `tests/validation-trial.test.ts` 共 13/13 通过，包含经公开 HTTP 返回异常样本的夹具；`npm run typecheck` 通过。这不是目标机测量。
- **未解决的 v3 边界**：当非关键负载的总体下限高于关键负载下限等自定义门槛组合出现时，已确认区间低于某一验收线仍可能得到保守的 `INCONCLUSIVE`，不会因此错误通过，但会隐藏已确认未达线。旧 v3 是已冻结的统计身份，不能静默改写其判定；需通过版本化规则和历史兼容测试修复。
- 发现冻结证据前只核对性能样本数量、身份和正值，可能把数值已变化的样本与旧的通过结论一起打包。冻结、人工批准和交付前现按正式与复验各自保存的样本、冻结方案和门禁版本重算；混入其他轮次、额外样本、变更统计摘要均会阻断新批准。
- 执行与证据复核共用方案兼容性规则，除清单、参数及采样外，还核对资源、关键负载、权重和 evaluator 内冻结的统计方案。新批准要求 v3 真实区间；旧点估计实验保留，已有历史批准按原口径读取并单独核验。`tests/testpack-compatibility.test.ts`、`tests/customer-summary.test.ts` 验证策略和报告；HTTP/CLI 审批夹具覆盖 v3、历史 v2 阻断、样本改动及两轮混用。
- 网页审阅入口读取服务端结论：旧点估计、只做正确性测试或缺少原 Runner 计划的记录不显示新的批准按钮，报告解释缺少的依据；已有批准与交付仍分别显示。报告中的验证通过保持原实验含义，不因新门禁回写为失败。
- 新冻结和新批准还核对各自保存的 RPC 计划、测量单位、参数、原始命令输出、候选源码身份和基线摘要；命令输出达到保留上限时按可能截断拒绝。现有 Runner 当时对被测库摘要进行检查，但未独立保存候选二进制本身，评价器与 benchmark 的可执行文件摘要由评价程序报告，控制端无法事后独立核验它们。旧批准没有原执行计划时仍按既有证据读取，不补造记录。
- 离线核验入口要求从可信渠道取得归档 SHA-256，检查归档和清单每项内容，不解包或执行脚本。具体命令、大小上限及信任边界见[证据完整性核验](../guides/evidence-verification.md)；完整性通过不表示结果经过独立统计复算，也不表示原件经过脱敏。
- 增加 `corepilot evidence verify <归档> --sha256 <可信摘要> --recalculate-performance --json`：核验归档后分别读取两轮各自的样本和固定方案，复用现有 v3 算法重算并比对当时的统计记录；区分一致、缺失、旧版、不支持、无效、超限和不一致。归档、输入与计算规模均有上限；此操作不执行归档内脚本。集成后的归档、统计与证据关联测试 18/18 通过，包括重签改动样本、混用两轮、无效参数、旧版和资源上限。无服务 CLI 使用夹具验证；未取得本轮真实硬件样本，也不能据此证明来源、实验有效性或公开安全。
- 统计区间依赖固定采样与分块假设，固定测量顺序仍可能产生系统偏差。没有本轮目标机 A/A 重复实验或人工对照，不能宣称误报率已校准或给出新增性能收益。

### 恢复、持久化和空候选

- **创建请求**：试跑与分支构建支持持久请求标识、内容摘要及原子关闭栅栏；已有记录的同键重放先返回原作业，不重新读取当前分支或方案。浏览器仅保存随机请求 ID，回执丢失后可查询或关闭尚未创建的请求；CLI 可用 `--request-id`。本地 HTTP、进程竞争和浏览器夹具覆盖重启、并发、分支变化、同键冲突及关闭竞态，未模拟真实断电；浏览器清除站点存储、跨浏览器或各标签分别发起时不共享 ID。旧无键调用保留原行为。
- **实例身份**：Runner SQLite 原子创建随机数据库身份；正式实验、复现、独立测试、试跑和分支构建在提交前固定它，并通过受保护路径核对提交、查询、取消、测量和 HTTP 上传。相同地址换用另一数据库时保留原作业为未知；旧记录未保存身份时不补造，本地可确认的准备失败仍保留原状态。Node 22.22.2 对正式 RPC、复现、独立测试及本地 Runner 身份相关测试 51/51、试跑请求与恢复 5/5、测试质量与审阅 7/7 通过；浏览器夹具另覆盖原作业恢复。详见 [Runner 数据库身份与恢复边界](../architecture/runner-store-identity.md)。该机制不证明数据库副本、恶意伪装或 SSH 与 Runner 同机。
- **历史方案提示**：已资格化旧生成适配器保留原资格和审阅人，但共享预检阻止新的正式任务并指向新建方案；未获资格草稿可以更新。Node 22.22.2 公开预检及方案审阅 8/8、Playwright 1/1 通过，均为隔离夹具。

- **恢复**：查询全部处于活动或需对账的工作流，不受网页列表 200 条分页限制；Workflow 与 Task 的中断写入同事务，损坏的任务引用单独记录问题，不影响其他任务或改写已有批准。待核对的远端作业保留原 ID。
- **继续要求的会话记录**：集成提交 `20b5678` 的浏览器全量为 92/93，失败项在任务继续后只读取了底层会话记录第一页；检查浏览器 trace 发现用户要求所在的后续事件还因追加在长提示末尾而被事件展示截断。原始会话保留了内容，但页面可能看不到。现在将用户继续要求放在生成上下文之前，并对这类有 16384 字符上限的要求保留完整事件；其余事件仍保持原有展示上限。浏览器测试按游标遍历会话并检查长要求首尾，源码模式也覆盖长度上限；不改写历史会话，也不声称修复了模型或服务中断前尚未持久化的请求。
- **观察断线**：组合全量 Node 回归在 `optimization-report-flow.test.ts` 中出现一次本机 `fetch failed`，单项原版本重跑通过；现有诊断未保存底层网络原因，不能断言其根因。暴露出的产品缺口是 CLI 观察遇一次连接错误就中止；现在状态与报告的只读查询最多重试 3 次，打印断线/恢复提示，持续失败保留原任务 ID 并报告未知，403 等服务端拒绝不重试；不会重新创建任务、实验或取消执行。故障注入测试先复现旧行为，修复后的连接中断、持续失败、权限拒绝、报告恢复和已有引导工作流相关测试 9/9 通过。此修复不证明该次偶发网络错误的根因，原全量失败留痕不得抹去。
- **事务**：任务创建同时保存 Task、Workflow 和请求身份；同一请求竞争时复用已保存的结果。执行终态同时保存 Workflow 与 Task，失败时保留候选和实验，并尝试记录可恢复诊断。复现创建同时保存实验与其工作流引用；旧版本留下的未确认孤儿可在复现说明中看到，须按原 ID 核对 Runner，不能自动重发。
- **空候选**：提交与 checkpoint 共用源码筛选，仅有明确识别的未跟踪构建产物时拒绝创建候选或实验。Git 已提交但会话未保存时重用原 commit、tree 与哈希清单；旧记录缺少恢复依据则保留现场并明确报错。该筛选目前不是所有构建系统产物的完整识别器。
- **正式候选恢复**：通过公开 HTTP、Git、SQLite 和本地模型夹具复现 Candidate 写入后会话 checkpoint 丢失时重复创建候选。现将 Candidate 与 Workflow 引用同事务保存；恢复仅在 task、hypothesis、commit/tree、归档及文件身份一致且不存在已有实验时复用原 ID。陈旧并发提案、历史重复或身份冲突均停止并保留现场，不按相同 tree 合并不同 commit。集成后的候选原子性、会话恢复及任务创建测试 13/13 通过。
- **正式实验恢复**：会话先固定实验创建意图，Experiment 与 Workflow 引用事务保存；中断后按相同身份核对，只在未发现已提交计划或执行观测时继续创建。旧版未关联且仍在活动或未知的实验阻断后续调查，保留原 ID。已有本地实验的进程状态未知时不自动重跑。
- **取消与未知状态**：提交响应丢失、取消未确认或 Runner 查询 404 均不证明未执行或已停止；系统查询原 ID，不自动重新提交。未知诊断与实验评价分开，保留已有评价和原始测量；无法持久化未知状态时向上报告未知，不能声称落库成功。不同已确认终态发生冲突时保留原记录并要求核对。Runner 实例身份与历史孤儿处置仍需维护者核对，不能宣称跨会话、数据库和 Runner 原子提交。
- **独立测试、试跑与分支构建**：仅明确的提交前拒绝才作为提交失败；409、5xx、断连或取消回执丢失保留未知，按原 ID 对账。控制端在试跑 `SUBMITTING` 阶段重启后继续查询原作业，404 不触发重新提交。网页提供核对原作业入口；Node 22 的测试与审阅 25/25、相关网页交互 3/3 通过，包含本地 Runner 接收后由代理返回错误的场景。旧版已经误记为 FAILED 的历史记录不自动改写。
- **复现提交**：新复现先在 SQLite 同一事务固定版本化意图、Runner 计划和胜出的目录，再允许一次提交；恢复时已有计划不因 404 再次 POST。取消与停止确认分别持久记录，并发准备使用独立目录；有计划的旧记录按原 ID 核对。已核对的历史版本均先保存计划再提交，其他更早或外部写入的数据不能作同样保证。目标机中失败准备留下的暂存目录不自动清除。合入后的 Node 22 复现、终态和事务测试 29/29 通过。
- **开发实验中断**：公开工作流使用持久会话时，即使 Agent 会话抛错，或用户取消与 Runner 状态未知同时发生，原开发实验未确认停止也保持 `INTERRUPTED` 并保留作业 ID；恢复时先核对，不重交作业。Node 22 下两项 HTTP/会话竞态及模型代理测试 3/3 通过，均为本地夹具。
- **Runner 终态与派生评价**：保存新的 Runner 原始终态快照，重新查询不会覆盖控制端评价；不同的终态事实停止对账。实际本地 Runner 的取消路径可能先确认终态、再释放队列，释放时间允许单向补齐，其余资源事实仍不接受变更；旧记录不补造快照。Node 22 下这组恢复、队列释放、代理和开发中断测试 9/9 通过。
- **实验评价与假设结果**：正式验证、复验和确认失败的评价、假设结果及假设状态在单个 SQLite 事务中保存；中途写入失败、其他连接先修改或已有结果冲突时回滚。完全相同的重放保留记录和时间；旧评价一致但缺结果时可补写，未知实验不产生假设结果。针对性事务与 RPC 17/17、公开 HTTP 确认丢失恢复 1/1 通过；Runner 的命令和原始测量仍独立同步，不宣称跨 Runner 原子提交。存储接口调整不需数据库迁移，但仓库外自定义 `OptimizationStore` 实现须同步新接口。
- **本地原始事实与并发状态**：本地验证的命令、测量和评价现在随假设结果同事务提交；写入中途失败不留下半套样本，也不把存储错误写成实验失败。旧实验若已有无法证明完整的本地事实，保留并阻断自动追加。Runner 状态、计划和未知标记通过当前记录比较后写入，陈旧连接不得覆盖新终态。合入复现修改后，Node 22 的本地事务、RPC/CAS、复现及公开 HTTP 故障测试 46/46 通过；多个实例在正式计划保存前同时进入远端暂存的隔离仍待完善，数据库持续不可用时未提交的本地输出也没有持久化 spool。
