# 测试质量、测量可信度与结果复现

更新：2026-10-30。网页与 CLI 使用同一套应用服务、SQLite 事实和 RPC Runner。本页描述当前代码能力；本地进程/RPC 测试不代表飞腾目标机上的性能验收。

## 先确认测试能发现错误

在「构建与验证 → 配置当前函数的测试方案 → 测试条件」展开「测试覆盖与已知错误检验」。

1. 填写适用于该 API 的覆盖维度、依据和逻辑输入 ID。覆盖状态可以是有输入覆盖、不适用或尚未确认。尺寸/向量尾部、stride/ROI、别名、对齐及浮点边界按实际函数选择。
2. 对选定错误添加检验，例如漏算尾部。上传与被测库接口一致的错误实现源文件；在「测试代码」的测试程序构建脚本中，将它编译到 `runtime_root/sensitivity/<文件>`。表单中的产物路径填写 `sensitivity/<文件>`。
3. 保存并试运行。系统将**同一份正确性程序**用于正常库和错误实现，保留实际执行命令、产物身份、原始测量和发现错误的输入。

只有有效的结构化正确性 `FAIL` 才算识别了声明缺陷。正常实现 PASS、崩溃、编译失败、缺失测量均不能替代识别证据。错误检验的结果是诊断 Observation，不混入正式正确性通过数。

已配置的错误实现必须全部被识别，才能通过本版试跑和审阅启用。未配置的旧方案仍可使用，但报告明确显示辨别力未验证。识别几个错误不证明完整 API 正确性。

覆盖方案保存在 evaluator 的 `correctness/quality-plan.json`，进入版本摘要，并可随测试包查看、下载。AI 起草正确性代码时可以同时提出覆盖清单、错误实现和构建步骤；已有的用户质量方案不会被生成结果覆盖。

逻辑输入、线程/绑核展开和性能采样分别计数。2 个输入 × 4 种运行条件是 8 次正确性执行，仍只有 2 个逻辑输入。

发现反例时，把可重建的参数、生成规则、seed、实际/期望结果和影响范围保存在用例及支持文件中。已审阅方案保持只读；从接入流程建立新版本，导入已有脚本并补充反例，再试跑和审阅。原实验、旧资格和交付记录保留；当前尚无自动撤回历史交付或一键派生全部测试资产的功能。

## Runner 统一排队

新 Runner 对全部 RPC 实验使用一个持久 FIFO 执行通道，包括分支构建、开发 benchmark/profiling、测试试跑、正式实验与复验。首版按整个实验独占机器，优先让本系统的作业不相互干扰；尚未按不相交 CPU 集合并行调度。

网页试跑和任务详情、CLI `workflow status` 展示 Runner 阶段、排队信息和资源等待。实验的 `observed_context.runner_queue` 留存入队、取得和释放时刻；`measurement_environment` 留存执行前后负载、可用内存及可获取的 CPU0 频率/governor 等信息。不可获取的值为 `null`，CPU0 观测不冒充所有测试核的频率。

排队取消不会启动子进程。运行中的取消需等进程结束确认。Runner 重启后，原 RUNNING 记录成为 UNKNOWN 并保留占用；等待队列不会直接越过它。维护者检查原进程及其子进程确已停止后，可记录释放依据：

```text
corepilot-runner confirm-stopped --endpoint <Runner 地址> --experiment <原实验 ID> --reviewer <维护者> --reason <检查与停止依据>
```

凭据从 `COREPILOT_RUNNER_TOKEN` 环境变量读取。该操作只保存停止确认并释放队列，不把旧 UNKNOWN 实验改写为成功；本机仍持有活动进程句柄时拒绝释放。

队列协调同一 Runner 管理的作业。其他用户的进程、另一 Runner 实例或外部服务仍可能影响硬件，需结合负载观测和 A/A 校准判断。

## 真实统计区间

测试条件的「重复测量」预设启用 `paired-block-bootstrap-v1`：默认每端 9 个样本、4000 次重采样、相邻样本分块长度 2、95% 置信水平。参数可在高级区修改，保存后进入 evaluator 身份；模型不能自行更改已冻结条件。

同一 workload 内按相同样本序号配对，baseline/candidate 使用相同重采样索引；分块保留相邻样本的部分相关性。总体区间对应固定 workload 权重的几何平均，逐负载区间按声明负载数做 Bonferroni 校正。原始样本、方法版本、参数、seed 和样本摘要随结果保存。

新统计 gate 同时检查总体收益、总体下限、全部负载非退化和关键负载下限。明确未达线为 FAILED，区间跨线或样本少于冻结方案的最少要求为 INCONCLUSIVE，缺失/重复/无效样本为 INVALID。证据不足时保存当前候选并停止验证，不要求模型修改算法解决噪声，也不自动反复加测直到通过。采样方案改变需要新测试版本。

这是在固定采样、代表性负载和分块假设下的统计估计；不能保证任意噪声分布或任意多轮候选选择后的整体误报率。首轮和独立复验分别报告，不选择较好一轮或静默混合样本。

未声明 `statistics` 的历史方案继续使用 gate v2 的中位数比值/外部下界口径，缺下界时使用点估计。新方案为 gate v3。历史 C002 等案例的实验、资格、批准和统计含义均不回写；单独配置 `confidence_level = 0.95` 不代表已有真实区间。

新批准要求正式实验和独立复验均有 evaluator 冻结的 `paired-block-bootstrap-v1` 统计方案和通过的 v3 区间；仅有历史 v2 点估计时，原实验仍按原口径显示，但要取得新的批准，需审阅新版测试方案并重新执行两次实验。已经批准的历史记录不因此改写；其后的交付仍须核对已有批准、证据和可用的原始记录。执行前及批准前共用方案兼容性检查，检查负载权重、关键负载、采样、资源和统计规则与评价器资产一致。冻结及批准时按两次实验各自的原始样本重算，拒绝样本、统计摘要和结果不一致的记录；无法重算的旧记录需要核对，不能补造。

配对分块区间不消除固定执行顺序造成的系统偏差。`paired` 每组先执行基线、后执行候选；应结合具体负载选择合理的交替顺序并在目标机开展 A/A 校准。现有 A/A 不会自动证明误报率，变更已冻结的顺序或统计方案必须产生新的评价器身份和相应资格。

准备新的批准证据、记录人工批准和开始源码交付前，系统分别从正式实验与复验各自保存的原始样本重算其门禁，并与冻结方案及当时保存的结果核对。样本、负载、统计摘要或结论不匹配时停止该操作，保留历史记录并提示重新验证。旧 gate v2 曾允许外部提供下界；核对时保留该下界，不将它声称为能够由样本独立算出的置信区间。缺少可核对的旧门禁数据时，不能为其新建批准，应在现有冻结方案和目标机条件下重新验证。

新冻结或新批准还要求正式实验和复验各自保留 RPC 计划及命令输出：计划须绑定冻结候选源码与评价器；正确性、各负载参数及每条秒单位样本须对应计划和命令输出；基线摘要须匹配冻结基线，同一轮正确性和候选测量须引用同一候选库摘要。每个负载内两端 benchmark 的自报摘要须一致；当前 Runner 在首次正式实验另有全负载相同的限制，复验核对允许不同负载使用各自的 benchmark。Runner 在执行期间会分别计算并核对被测库摘要，但当前协议没有另行持久化 Runner 计算出的候选库摘要，控制端也没有取得二进制原件；保存的命令输出和测量均来自同一 Runner，事后对账不等于重新独立验证二进制。评价程序/benchmark 摘要由程序自报，同样不是控制端独立验算。

命令输出达到 Runner 保留上限时无法确定是否已截断，新批准会按证据不足停止。缺少 RPC 计划、输出或产物身份的历史结果仍可查看；不能凭空补造身份来取得新批准。已有人工批准及冻结证据保留原有语义，不能由这项检查反推历史执行已取得新增证明。

## 用 A/A 检查测量偏差

选择「重复测量」并保存，在「试运行」点击「运行 A/A 测量校准」。Runner 新建开发实验，构建一次当前库，把**同一个产物**用于两端，在相同条件下交替测量；不使用外部比较基线，不调用模型。

结果显示区间兼容 1×、检测到偏差或证据不足，并提供区间与原始分析。宽区间仍代表测量不稳定，兼容 1× 不等于已经精确。检查计时范围、线程/绑核、系统负载、缓存和采样方案后，再做两库对比。A/A 不替代两库资格试跑，不作为优化收益；单次 A/A 不产生经验误报率。

```text
corepilot project trial <项目 ID> <Package ID> <版本> <目标 ID> --calibrate
corepilot project trial-status <项目 ID> <试跑 ID>
```

`--calibrate` 与 `--compare` 互斥。两者使用相同的 `validation-trials` HTTP 服务。

## 客户报告和恢复

「优化报告」先展示当前候选、冻结源码、首轮/复验收益、实际统计区间、逻辑输入/执行次数、已发现退化、资源等待、适用范围及下一步。按 workload 的实际尺寸、类型、线程和绑核参数分组；组内数字是描述性点估计，分组可重叠，不新增隐含验收线。

只有正式实验和其后的独立复验都完整、有效，且 evaluator、基线和机器身份一致，报告才给出当前交付建议。后续复验失败会更新当前建议，原通过、批准与源码交付事实仍保留。

源码提交父版本、当前库比较基线和外部库基线按实际身份阅读。相对外部库或较老版本的收益，不能视为本次源码提交的净增益。

恢复入口按事实选择：

| 当前情况 | 下一步 |
| --- | --- |
| 仍在运行 | 观察原作业；关闭页面不取消 Runner |
| 会话中断或预算耗尽 | `corepilot workflow resume <ID>` 恢复原会话 |
| evaluator、执行环境或统计证据受阻 | 修复原因后 `corepilot workflow retry-validation <ID>`，使用原冻结候选创建新实验 |
| 远端状态未知 | 先核对原实验 ID，不能当作已失败重新启动 |
| 正式实验与复验完成 | 人工审阅源码、范围和证据，再决定交付 |

测试方案资格审阅、领域 Approval 和 Git 源码交付分别展示。普通报告不会自动批准；公开审阅入口支持冻结证据并记录具名人工决定，之后才可单独交付。历史交付不补造批准。

## 从冻结源码重建复现

在报告点击「在 Runner 重建复现」，或执行：

```text
corepilot workflow reproduce <工作流 ID> --plan --json
corepilot workflow reproduce <工作流 ID> --json
corepilot workflow status <工作流 ID> --json
corepilot workflow reproduce <工作流 ID> --cancel
```

复现使用原冻结 Candidate 和保存的 RPC 构建/测试计划。系统检查原机器身份、Runner 排队及资源约束能力，导出冻结 Git 提交，在 Runner 新的 `reproductions/<工作流>/<实验>/` 目录解包并构建；源码、build、evaluator、runtime 和日志分别定位。重新导出的源码必须匹配原摘要。原比较基线和 qualified evaluator 身份保持固定，缺失或变化时明确失败，不换成当前默认基线。

每次新的复现创建一个 `REVALIDATION` 实验，保留原审批、交付和全部历史。观察中断后「核对并继续原复现」先查询原 ID；传输重试不生成第二个实验。取消等待 Runner 确认。网页可下载复现计划与身份清单；完整命令、资源观测和新样本继续进入共享报告。

创建复现实验及其工作流引用在同一事务保存；保存中断不会只留下新实验。旧版本可能遗留未关联且尚未确认终态的复现实验；`workflow reproduce <工作流 ID> --plan --json` 的 `unlinked_reproductions` 列出这些 ID 和已记录状态。遇到此情况时，先由维护者核对原 Runner 作业，不能自动把它判为失败、释放资源或提交新实验。

旧任务若没有保存原 RPC 计划、机器身份或冻结测试快照，会说明缺失内容，不能伪造可复现性。此入口依赖原 Git 对象、qualified 测试资产和冻结基线仍可访问；它不是离线部署包。
